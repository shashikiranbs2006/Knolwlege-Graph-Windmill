How the wind knowledge graph answers a question

Current version (v3). Each farm keeps its data in its own database and publishes it through Ontop in one shared vocabulary. A hub holds a validated copy of every farm's knowledge records (turbines, alarms, diagnoses, repairs). Measurements (power, wind speed) are not copied: the assistant asks each farm for them live. One assistant first picks a tool, then writes the answer from the returned rows only.

The big picture: two tools, one assistant

What changed in v3. The old picture sent every question to the hub, so a question about measurements returned nothing. Now the LLM chooses: ask the hub (knowledge) or ask the farms (measurements). The LLM never writes multi-farm SPARQL and never sees an endpoint; for measurements it returns only parameters, which the code validates and runs.

Before any question: how each source reaches the hub

Every row ends in the same wind-core vocabulary even though the sources are laid out differently. The hub harvests farms A and B from their Ontop endpoints with a CONSTRUCT query per class, checks them against the SHACL shapes, and loads a farm only if it conforms. The SCADA readings are not copied: they stay at the farm and are asked live by the farm_metric tool. Farm C is a Neo4j graph exported to a file, because Ontop cannot read Neo4j (not SHACL-checked; no farm_metric adapter yet).

Measurement path (live at the farms) new

M1. The LLM returns parameters onlymetric (Power, WindSpeed, ...), aggregate (avg, min, max, sum, count), per farm / turbine / month, farms, date window. No SPARQL.
M2. Code validates themfarm_metrics.py checks every value against hub/farms.csv: unknown farm, unpublished or withheld signal, bad date are refused. Scope rule enforced.
M3. Ask each farm live, in parallelOne aggregate query per farm to its own Ontop. AVG and COUNT run as SQL at the farm, so only a few rows travel (about 0.3 s each). Timeout per farm from the registry.
M4. Ontop and PostgreSQL at each farmFarm A and farm B answer independently. Raw readings never leave the farm.
M5. Merge and labelNames any farm that was offline or did not publish the signal; refuses to merge unequal units; adds capacity factor (average power / rated power) and a ranking caveat, because both farms use the same turbine class.
↓ rows from either path
10. The LLM writes the answer, from the rows onlyFirst 30 rows. Synthetic and curated records are labelled; a farm that did not answer is always named.
11. The reply is assembledAnswer, SPARQL, columns and rows, scope and why, model, where it was answered, and for measurements which farms answered.
12. The page shows itAnswer, table, SPARQL. Measurements carry a blue "Live farm query" badge: "measured just now by asking each farm's own endpoint". Farm A answers keep the at-the-farm replay.
Checked on the running stack: average power per farm returns Kelmarsh 515.0 kW (capacity factor 0.251, 285,693 readings) and Penmanshiel 527.3 kW (0.257, 324,854 readings) in about 1.5 s, equal to asking each Ontop directly. Stop one Ontop and the answer names that farm and still gives the other.

Adding a new source

The pattern is the same every time: map the source to the existing wind-core terms, so the assistant and the question box do not change.

New sourceSteps
A CSV fileAdd a table in db/schema.sql, load it in db/load.sql (or a prepare_*.py), add a mapping rule in vkg/mapping.obda, regenerate mapping.ttl, restart Ontop, re-run hub/build_hub.py.
Another SQL databaseGive it its own Ontop node like farm B (schema, mapping.obda, ontop.properties, db and ontop services in compose.yaml) and a row in hub/farms.csv. Fill in its signals and withheld_signals and it is asked live by farm_metric with no code change.
A REST APILoad the JSON into PostgreSQL with a small loader and map it like a CSV, or export RDF as neo4j_farm_c.py does. For live measurements, a small adapter that implements farm_metric by calling the API (phase 3).
A graph database (Neo4j)A Cypher query per class in an exporter script, a CSV to match names to shared codes, picked up by build_hub.py. It is a copy; re-run to refresh. A Cypher adapter for live measurements is planned (phase 3).
Every sourceReuse wind: terms (new ones in vkg/ontology.ttl are seen by the LLM automatically), add a shape in vkg/shapes.ttl for any new record type, add an example query in queries/.

Which parts are real

The SCADA readings and alarms on farms A (Kelmarsh) and B (Penmanshiel) are real open data from 2016. The maintenance and work-order records are synthetic and labelled synthetic_demo, so repair differences between farms are illustrations, not findings. The alarm-to-fault rules and their confidence values are illustrative demo rules, labelled curated_demo. Farm C is a small fictional Neo4j graph. Hub copies are as old as the last run of hub/build_hub.py; measurements are live.

Known limits of this version

One metric per question. Per-turbine grouping but no filter by turbine name. Farm C has no live measurement adapter yet. The hub copy is refreshed by hand until a scheduled rebuild is added (phase 2).
