Where should the hub get its data? Options for the wind knowledge graph

Research report, 15 Nov 2026. Question: should the hub keep copying each farm's knowledge records (today), or become a virtual / federated router that sends each question to the farms and merges the answers? Based on the code in this folder, the git history and earlier session logs, measurements on the running stack, and published sources (links at the end). Nothing in the project was changed.

Short answer

Neither pure design is right. The current hub is a good design for knowledge (turbines, alarms, diagnoses, repairs, governance) and a poor one for measurements (power, wind speed). Your federated idea is the right idea for measurements, and the wrong one for knowledge. The best answer is a hybrid: keep the validated hub for knowledge, and add a small farm-query path that sends one safe aggregate query to each farm's Ontop and merges the numbers. The LLM chooses between the two as tools, instead of writing federated SPARQL itself.

This is cheap here. On your running stack, "average power per farm" through SPARQL SERVICE from the hub returned the right numbers (Kelmarsh 515 kW, Penmanshiel 527 kW) in 0.6 s. The same question fails today only because the assistant is forbidden to use SERVICE and the hub holds no observations.

1. What the project does today (confirmed in the code)

  • Farms. Each farm has its own PostgreSQL and its own Ontop mapping to the shared wind-core vocabulary (vkg/mapping.obda, farm_b/mapping.obda). Farm C is a fictional Neo4j graph exported to a file by neo4j_farm_c.py.
  • Hub. hub/build_hub.py runs one SPARQL CONSTRUCT per class on each farm's Ontop, validates the result with SHACL, and writes one named graph per farm into hub.trig (about 207k triples for Kelmarsh, 239k for Penmanshiel, 76 MB file). If a farm is down, the last good snapshot stays. Observations (the SCADA readings) are deliberately not harvested.
  • Registry. hub/farms.csv lists endpoint, what each farm exposes and withholds, as free text. The code does not yet use it to route anything.
  • Assistant. assistant.py sends the question and an ontology summary to the LLM, which writes one SELECT. Code checks it (SELECT only, LIMIT 50, SERVICE and FROM forbidden, farm scope enforced) and runs it on the hub only. Scope (one farm or all) is guessed from wording by detect_scope.

Why the earlier SERVICE version was replaced

Git history starts after the switch (the first commit already has the hub), so I used the earlier session logs. An earlier build did use SERVICE <ontop> {…} blocks written by the LLM, with a prompt listing the farm endpoints. On 14 Nov a request merged two sites into one hub with one named graph per farm. The assistant's reasoning then was: SERVICE cannot produce named graphs, Fuseki has no virtual named graphs, and SHACL checking, farm-down resilience and a single place for curated RDF 1.2 annotations all needed a local copy. The observations were left out because of size (~314k readings per farm-year at the time). I found no record that federation was slow or failed. It was a design choice (scoping, validation, availability), not a measured failure. That matters, because the measurements below show the choice was right for knowledge and unnecessary for aggregates.

3. All the options

Scores: speed = typical question; effort = work in this codebase, in working days for one person; privacy = how much data leaves the farm.

A. Current design: materialised knowledge hub keep, extend

How
Harvest CONSTRUCT copies of non-time-series records into Fuseki, SHACL-gated, one graph per farm.
Fit
Excellent for fault diagnosis and cross-farm repair learning. Poor for any question about measurements.
Pros
Fast (0.2 s), works when a farm is down, SHACL gate, RDF 1.2 annotations in one place, easy for an LLM (one endpoint, GRAPH ?g pattern), easy to audit.
Cons
Data goes stale until rebuilt (about 2 minutes by hand). A copy of records exists outside the farm. Needs a refresh job per farm. No measurements.
Privacy
Medium. The farm controls what is mapped, but mapped records are copied. Withholding is by not mapping (farm B's crew names).
Speed / effort
Fast / already done. A scheduled rebuild is about 1 day.
Failure modes
Stale hub answers read as current (the registry shows harvest time, the answer text does not). One farm's schema change breaks the harvest, and the last snapshot hides it quietly.

B. Pure federation with SPARQL 1.1 SERVICE (Jena/Fuseki) use for measurements

How
The hub keeps only ontology, registry and curated knowledge. Queries contain SERVICE <farm> {…} blocks per farm (W3C SPARQL 1.1 Federated Query).
Fit
Matches your proposal. Measured above: good with pushdown, bad without.
Pros
No copy. Always live. Already in Jena. Farms keep full control of their endpoint.
Cons
The hub engine has no statistics about the farms and may pull raw rows (20 s case). All farms must be up. The LLM must write correct per-farm blocks, which is harder than one graph. No SHACL gate. Joins with hub knowledge cost 12x more.
Privacy
Best of the SPARQL options: only results travel, but the hub can ask any question the endpoint allows, so each endpoint needs authentication and a query allow-list.
Speed / effort
Fast for pushed aggregates, slow otherwise / 2 to 4 days if done through templates, more if the LLM writes it.
Failure modes
One slow farm stalls the answer; SERVICE SILENT hides a missing farm and gives a wrong "all farms" answer; unbounded SERVICE from LLM text is also an SSRF path, so the current ban is sensible.

C. Smarter federation engines (Comunica, RDF4J FedX, Semagrow) maybe later

How
A federation engine does source selection and join ordering. FedX sends ASK queries to find which source has which pattern, groups patterns that hit one source, and uses bind joins. Semagrow uses VoID statistics. Comunica 3.0 added source grouping, bound joins and pruning of empty sources.
Fit
Only worth it if you have many endpoints and unpredictable queries. With 2 to 5 farms and a known vocabulary, the gain over hand-pushed SERVICE is small. Several of these are research-grade; I found no recent release notes for Semagrow, so verify before depending on it.
Pros
Automatic pushdown and join ordering. FedX is a drop-in part of RDF4J.
Cons
Another engine to run. Source selection costs extra requests. Ontop endpoints are slower to answer ASK probes than native triple stores. Still cannot gate with SHACL.
Privacy / speed
Same as B / usually better than naive B, still behind materialised.
Effort / failure
3 to 6 days to integrate and test / wrong source choice gives silent missing farms; benchmark claims are mostly from the projects' own papers.

D. Ontop over a federated SQL layer (Trino, Dremio, Denodo, Teiid) not now

How
One Ontop at the hub maps to the shared ontology; below it Trino (or Dremio, Denodo, Teiid) exposes every farm's database as one SQL catalogue. SPARQL becomes SQL, and cross-farm joins become federated SQL. Ontop's guide lists these federators as supported (Trino since 5.0.2, Dremio since 4.1, Teiid since 4.1.1). An ITC case study federated PostgreSQL sources with Trino plus Ontop; it reports open issues in identity alignment, schema harmonisation, performance and governance. Optique at Statoil and Siemens used the same idea (OBDA over federated back ends) with its own engines, ExaStream for streams and Exareme for static data.
Fit
Strong for one organisation with many databases. Weak for farms owned by different companies.
Pros
One mapping layer and true SQL pushdown, including time series. Handles measurements well.
Cons
Needs every farm to open a database connection to the hub, which removes the Ontop mapping as the governance boundary (Trino sees raw tables). Cross-source joins are the known cost. One more large service (Trino) to run. Farm C (Neo4j) is not covered.
Privacy
Worst of the options: the hub holds credentials to every farm database.
Speed / effort
Good for single-farm aggregates, uncertain for joins / 8 to 15 days plus security work.
Failure modes
Hidden full-table scans, credential sprawl, a schema change at any farm breaks hub mappings.

E. Commercial virtual graphs (Stardog, GraphDB) not now

How
Stardog maps relational data with R2RML and lets you choose per source whether to query live (virtual) or copy in. GraphDB advertises virtualisation beyond simple federation, and a community post says it embeds Ontop (I found no official page confirming this).
Fit
Closest to the "switch per source" idea, in one product.
Pros
Mixed virtual and materialised in one query engine; vendor support; Stardog reports large speedups for heterogeneous federation on its own blog.
Cons
Licences and cost. Lock-in. A Stardog virtual graph on a non-Stardog SPARQL endpoint reportedly needed SERVICE instead. You would give up Ontop and Fuseki, which the research paper and the team lead follow.
Privacy / speed / effort
Like D / good / 10+ days and a procurement decision.

F. Hybrid: copy small knowledge, federate big measurements recommended core

How
Keep option A for knowledge. Add a farm-query path for time series: Python code sends a parameterised aggregate (metric, farms, time window, group by) to each farm's Ontop, in parallel, with timeouts, then merges and labels the rows.
Fit
Matches the data: knowledge is small, validated and joined a lot; measurements are large, change daily, and mostly asked as aggregates.
Pros
Uses what already works. Measured at about 0.6 s. Raw readings never leave the farm; only the aggregate does. A farm that is down is reported by name, not hidden.
Cons
Two paths to maintain. Some questions need both (for example "alarms at times of high temperature across farms"); those need a join in code or a materialised aggregate (option G).
Privacy
Good. The aggregate template is the policy: it can refuse per-turbine detail, small groups, or withheld signals.
Speed / effort
Fast / about 4 to 6 days (gateway, templates, registry columns, tests).
Failure modes
Different units or sampling between farms (kW vs MW, 10-minute vs 1-minute) give a wrong comparison; handled by checking wind:unit in the result and refusing to merge unequal units.

G. Materialise aggregates into the hub add when needed

How
Harvest daily (or hourly) per-turbine means, maxima and counts per signal as wind:Aggregate records. About 30k rows a year for 20 turbines and 4 signals at daily resolution (about 700k hourly).
Fit
Covers the common "compare farms over a year" and "trend before a fault" questions in the same graph as the knowledge, so joins are fast and SHACL applies.
Pros
One endpoint answers everything the daily resolution supports; works when a farm is down.
Cons
Stale by a day. Fine detail (a single gust, 10-minute spikes) is lost. Needs an aggregate view in each farm's SQL and a shape in SHACL.
Privacy / effort
Medium (derived, not raw) / 3 to 4 days.

H. LLM-side routing recommended for the assistant

Three variants
(1) Tools per capability. The LLM gets tools such as query_hub(sparql) and farm_metric(metric, agg, farms, window); the code does the fan-out. (2) Text-to-SPARQL against a federated endpoint (the LLM writes SERVICE blocks, your earlier design). (3) LLM plans sub-queries, one per farm, then a merge step.
Evidence
Agentic SPARQL (2026) evaluated LLM agents using SPARQL via MCP on a federated benchmark and reports that endpoint discovery and source selection remain hard and often produce slow queries; source metadata catalogues are largely missing. A multi-agent KBQA paper (AMA-KBQA) shows that onboarding a new graph can be just a wrapper, but its prototype commits to one route per question.
Verdict
Variant 1 is the safest: a typed tool call cannot leak a query to an unregistered endpoint, farm selection comes from the registry, and each farm's limits are enforced in code. Variant 3 is the next step once variant 1 works. Variant 2 has the highest failure rate and the weakest security, so keep the ban on SERVICE in LLM text.

I. Data spaces (Eclipse Dataspace Components, IDSA, Gaia-X) later, if farms are different companies

How
Each farm runs a connector that publishes a catalogue and enforces usage policy; the hub negotiates a contract before each transfer. EDC is open source and implements the IDSA Dataspace Protocol and Gaia-X trust framework; it includes a Federated Catalog and identity hub.
Fit
It solves who may ask what, not how to query. It would wrap options B or F, not replace them. I found no wind-specific dataspace in my search. A 2023 survey found documentation of the open-source connectors poor.
Effort
Weeks, with an identity and policy decision first. Out of scope for the pitch.

J. Neo4j and other graph farms in the federation

Options
(a) Today: export to RDF and load (stale, not SHACL-checked). (b) Same export but through the harvest path: run the exporter inside the build, validate with SHACL (RDF 1.2 annotations are the obstacle; flatten confidence onto Diagnosis nodes as farms A and B do). (c) A small adapter exposing the same farm_metric tool, implemented with a Cypher template; no SPARQL needed. (d) neosemantics (n10s) inside Neo4j to speak RDF. (e) Ontop over Neo4j's JDBC SQL-to-Cypher translator: Ontop does not support Neo4j, so that is research only.
Pick
(b) for knowledge, (c) for measurements. Both fit the recommended design; (e) does not exist as a supported path.

5. Recommendation and plan

Ranked

  1. F + H: hybrid with tool-based routing. Knowledge stays on the validated hub; measurements go through a farm-query tool.
  2. G on top: daily aggregates on the hub for fast, offline-safe trends.
  3. B as the engine inside the tool (or direct HTTP to each Ontop). Not exposed to LLM text.
  4. C, then I, only if the number of farms or companies grows. D and E: skip for this project.

Phases

PhaseWhatDone when
1 (about 4 days)Make farms.csv machine-readable (signals, units, capabilities, max rows, kind). Add farm_metric with 3 templates: aggregate per farm, per turbine, per month. Add it as a second tool in assistant.py. Keep SERVICE banned in LLM text."Average power across farms, which is highest" returns both farms with units, time window and a note about normalising by rated power.
2 (about 2 days)Failure handling: per-farm timeout, named missing farms in the answer, stale-snapshot age shown in answers, scheduled hub rebuild.Stopping one Ontop yields a partial answer that says which farm is missing.
3 (about 4 days)Daily aggregates materialised into the hub with a SHACL shape; Neo4j harvested through the build and a Cypher adapter for farm_metric.Trend-before-alarm questions answered on the hub alone.
4 (optional)LLM-planned multi-step queries; authenticated proxies and query allow-lists in front of each endpoint; a data-space connector only if farms are separate companies.Decided by real partners.

Adding a new API source

  1. Knowledge records: write a small exporter that emits wind-core terms (like neo4j_farm_c.py), run it in the build, SHACL-gate it, add a row to the registry.
  2. Measurements: either load the readings into a small SQL table and put an Ontop mapping on it (then it behaves like farm A or B), or write a 30-line adapter that implements farm_metric by calling the API. Declare its signals, units and limits in the registry.
  3. Nothing else changes: the assistant finds it through the registry.

6. Honest verdict

Is the current design acceptable? Yes, for what it claims: it is sound for knowledge, it is honest about copies and staleness, and it fails safely. The README already says time series stay at the farm. It is not acceptable as the whole answer for a "ask anything across farms" assistant, because a whole class of obvious questions returns nothing, and today the assistant cannot even say that those need a different path.

Is your federated proposal right? Half right. For measurements it is the correct idea, and my test shows it already works at 0.6 s. As a replacement for the hub it would be a step back: joins with curated knowledge became 12x slower, every farm must be up, the SHACL gate and last-good-snapshot behaviour disappear, and an LLM writing multi-endpoint SPARQL is the least reliable variant in the 2026 literature I found. What is worth keeping from your idea is the registry-driven routing and "no copy" for big data.

Where I disagree with earlier proposals. The review document (KG_review_architecture_and_stack.md) recommended federating knowledge with SERVICE. The project moved away from that, and my measurements support the move. The same document is right to avoid Trino-style stacks and to keep Neo4j out of the core.
